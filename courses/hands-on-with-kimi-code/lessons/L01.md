# Lesson 1: Reproduce the failure, survey it with the read-only lane

## Objective

By the end of this lesson you have `kimi` running in the course folder,
you have run the course's objective verification command, and you can
explain what "the starter fails" means in test names. No code is changed
in this lesson.

## Why this lesson exists

Most AI-written Python dies the same way: the demo input works, the real
input arrives, and the script crashes on row 3 — or worse, quietly
produces a wrong number. The fix does not start with a better prompt. It
starts with turning "it's broken" into a command that anyone can run and
get the same answer. Kimi Code adds a useful division of labor: built-in
subagents split the work — `explore` reads but cannot write, `plan`
plans but has no shell or write tools, and `coder` does the editing.
Surveying through the read-only lane means the exploration cannot break
anything.

## Warm-up (2 minutes)

Open `starter/report_tool.py` and read it top to bottom. It looks
reasonable: functions with docstrings, type hints, a CLI. This is exactly
what AI-generated code looks like — clean surface, missing behavior. Now
open `TASK.md` and keep it next to you.

## The lesson

Start `kimi` in the course folder. Ask for a read-only survey first — the
`explore` subagent reads files but cannot change them:

**"Use the explore subagent to read COURSE.md, TASK.md, and
starter/report_tool.py. Do not change any file. Report which behaviors the
tests expect that the starter does not have."**

While it reads, run the objective verification yourself in a terminal:

```bash
python verify.py starter --expect-failure
```

You should see the starter reproduce four real-world failure classes,
mapped to test names:

| Failing test | Real-world meaning |
| --- | --- |
| `test_load_json_records_returns_list_of_dicts` | the tool only handles CSV; the API scenario crashes |
| `test_unsupported_suffix_raises_value_error` | an `.xlsx` upload becomes a confusing crash instead of a clear rejection |
| `test_invalid_records_are_isolated_with_reasons` | one empty cell aborts the entire run — no partial report, no reason |
| `test_group_totals_are_rounded_to_two_decimals` | `0.1 + 0.2` prints as `0.30000000000000004` in your report |
| `test_write_report_creates_missing_parent_directories` | the tool cannot write into a fresh output directory |
| `test_run_scenario_writes_report_file`, `test_main_prints_summary_and_returns_zero` | end-to-end consequences of the above |

Then run the reviewed implementation the same way:

```bash
python verify.py solution
```

Both commands exit 0 — but they mean opposite things. The first proves the
starter is *correctly unfinished*; the second proves the target is
reachable. That pair is your completion evidence for the whole course.

## Exercise

Pick the scenario skin you most identify with (`excel-report`,
`data-monitor`, or `api-tool`), open its data file, and find the rows that
will be rejected. Write down, before running anything, which test each bad
row will trigger. Then check yourself against the table above — and have
`explore` confirm, not `coder` fix.

## Checkpoint

Run `python verify.py starter --expect-failure` and
`python verify.py solution`. You pass this lesson when you can answer,
without looking:

1. Which four behaviors separate starter from solution?
2. Why is "expected failure" a success condition, not a contradiction?
3. Which subagent can change files — and which two cannot?

## Expected evidence

The transcript of both commands, and your three answers. Keep them;
Lesson 4 will ask for them again.
